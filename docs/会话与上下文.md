# 用户/会话/上下文/缓存（增量实现）

网页版更新：当前增加真实注册/登录、服务端确认的用户ID，按操作在线程内创建SQLite连接；旧CLI的--user仍仅为本机调试入口。表结构新增accounts/logins/preferences/requests；长期偏好经网页明确保存，完整轮次和任务completed同事务提交。原文保留早期CLI设计说明，当前以README和《网页版-启动与边界》为准。

当前代码已接入SQLite会话和精确缓存；摘要在超预算时调用真实DeepSeek，没有代跑收费API。长期偏好、MCP和工具循环仍未实现。运行入口仍是本地开发CLI，尚未迁成CS服务。

## 1. SQLite存在哪里

本项目data/assistant.sqlite3，初次使用时建表：
- users：本机用户标识与创建时间。
- sessions：user_id、会话ID、创建时间，组合主键。
- turns：user_id、session_id、轮次序号、用户原文、助手完整回复；一行是一个完整轮次。
- summaries：按用户和会话隔离的摘要及已覆盖的through_turn；缓存派生资料，不替换原文。
- answer_cache：按用户/会话/请求指纹存完整回答，附过期时间。

暂不建独立messages表，因为还没有多条工具消息；接MCP循环时再迁移为完整消息/工具链结构，不把当前question/answer两列误当能容纳任意Agent轨迹。

所有会话内容、摘要和缓存读写都检查user_id+session_id；同用户不同会话也不共享缓存或上下文。插入轮次按预期旧轮数进行事务检查，防止另一进程更新后错误追加；并非生产级多用户平台。日志附运行ID、user_id、session_id，不记录正文或Key。

## 2. 如何使用

在项目目录执行：

```bash
../.venv-framework/bin/python -m hearthstone_assistant chat --user alice
```

不带--session会新建会话，记下屏幕打印的ID。每次进程问答一次，继续同一会话用：

```bash
../.venv-framework/bin/python -m hearthstone_assistant chat --user alice --session 你实际的会话ID
../.venv-framework/bin/python -m hearthstone_assistant sessions --user alice
../.venv-framework/bin/python -m hearthstone_assistant history --user alice --session 你实际的会话ID
```

用bob查alice的ID会拒绝；alice不指定ID再开会话也不会带入上次历史。sessions/history不请求模型；chat会请求，必要时额外摘要计费。当前没有交互式/new或/switch，不要输入这些当命令。

重要：--user是本地测试身份选择，不是登录认证！能操作同一Mac账户的人可以指定alice，也能读取SQLite文件。未来Web必须从认证后的服务端身份取得user_id，不能信任请求自报ID；数据库/日志还需OS权限、备份、保留/删除策略。本机程序不能被宣传为已实现安全公网多租户。

## 3. 上下文与摘要

完整原文留在SQLite；实际发送messages由memory/context.py选择。默认24000估计单位，使用UTF8字节+每消息余量，包含4096输出预留，绝不称为精确token。provider仍设max_tokens=1024。

小会话直接发未摘要原文；超出估计预算后分批把旧的完整轮次和已有摘要发给模型，总结目标、事实、否定条件、模式/版本与未解决问题。每批原文载荷最多12000字节，每用户请求最多3次摘要，单份摘要限制4000字节；尽量保留最近两轮原文，放不下时可继续压缩最近的完整轮次。缓存through_turn，下次只处理新旧轮次，不每次重发全部旧历史做摘要。

当前问题本身过大时在请求前拒绝；单轮原文太大/摘要失败/次数上限时停止，不无上限调用模型。现有缓存摘要可已更新，但本次新聊天仍未提交；这是派生缓存变化，不是半轮对话保存。摘要有损，原文保留用于history核对，不自动当新系统指令。

日志看summary_start/summary_saved和model_request.stage=summary；正常问答stage=chat，token要分别加总。没有摘要需要就不调用。摘要减少后续上下文，不保证省每一次请求费用，也不是数学上保证不会溢出；服务端窗口、精确tokenizer及工具schema加入后还需重新核算。

## 4. 精确回答缓存

缓存模块cache/生成SHA256指纹，包含完整实际messages（含system和摘要）、模型名、API地址、请求行为版本和输出参数；存储再按用户/会话隔离。默认15分钟，过期不命中；仅缓存完整stop回复，不缓存错误/半截内容。命中时明确显示缓存来源，不发新的主问答请求、不伪造流式打印。

这是一层保守的重复请求保护，**不能保证同一句话重复问就命中**：正常聊天追加了上一轮后，上下文变化，必须重新计算。特别是“这副套牌怎么样”“再加16”不能按问题字符串复用。跨会话也不复用，所以新开会话问相同问题仍可能计费。当前最能覆盖同一快照重复请求（例如完整回复已缓存、会话提交之前失败后重试），不是语义缓存。

```bash
../.venv-framework/bin/python -m hearthstone_assistant chat --user alice --session 你实际的会话ID --no-cache
```

--no-cache不读写本地回答缓存；不禁用上下文摘要缓存，也不控制供应商缓存。回答缓存检查在上下文准备后，所以已发生的摘要费用不能因回答缓存命中而撤销。

后续MCP卡牌查询更适合加“工具结果缓存”：按实体ID、模式/语言、数据版本与来源时间缓存，避免重复查数据。那时还需把数据快照/工具schema加入回答指纹，禁止沿用text-only-v1缓存协议。语义近似问题暂不命中，避免相近但相反的条件被混淆。

应用回答缓存可跳过整个主模型请求；供应商前缀缓存通常仍发API请求，不能理解为零费用。SQLite缓存含私有回答，不能公开数据库，不把哈希key误当加密。
